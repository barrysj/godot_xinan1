## 推荐实现边界

### 1. 内容定义与运行状态分离

建立带稳定字符串 ID 的自定义 Resource 类型。一个内容一份 `.tres`，字段分组、合法范围、拖拽图片引用，必要时提供中文提示与示例。字段命名和目录可由实施者合理选择。

建议类型：人物、敌人、装备、技能、事件及选项、地点、敌群、奖励池。能共用的单位属性/效果结构共用，不为每个角色写一个专门脚本。

资源只存静态定义；当前 HP、技能计数、持有物、穿戴、训练、阵位等必须留在运行状态，不能修改共享 Resource 导致多个单位互相污染。

使用明确内容目录和目录索引/清单。新增内容的注册路径应简单且适用于导出版本，不依赖只在编辑器下可用的文件枚举方式。稳定 ID 不随名称、文件排列或展示排序变化。

### 2. 有限、可组合的效果系统

先覆盖已有行为：伤害、治疗、护盾、生命/攻击/攻击间隔调整；已有目标规则及普攻计数触发。迁移时保留当前攻击顺序、数值含义和玩法，避免数据化同时重平衡。

事件先支持少量实际需要的条件与结果，例如资源门槛、拥有某人物/装备、给予装备、招募、训练、增减资源、进入奖励选择。条件显示与执行时都需检查，支付与发奖防止重复触发。无需构建任意脚本语言或无限复杂节点编辑器。

### 3. 内容接入与存档兼容

现有内容迁入资源并保留原有效果。战斗、队伍、背包、奖励资格、图鉴从同一内容来源读取，避免“图鉴已添加，实际游戏不可用”。人物身份与技能选择解耦，两个不同人物可以使用同一技能。

现有存档有整数角色 ID、固定装备字段和基于 seed 重建路线的逻辑。必须设计版本迁移映射；尤其注意内容池变化后，同一 seed 不应悄悄生成另一条已保存路线或待领取奖励。决定保存生成结果/内容版本等策略，并验证。

存档引用不存在的内容、重复 ID、无效效果应明确报错并保留原档，不能静默抹掉内容。沿用原子写入、失败回滚、结算和派遣只领取一次。测试使用独立夹具，不能覆盖用户真实 user:// 档案。

### 4. 用户实际录入流程

交付可复制的人物、装备、技能、事件等样例及清晰的内容目录入口。中文说明至少包含：

1. 在 Godot 文件系统面板复制示例并修改稳定 ID。
2. 在检查器填写名称、数值、文字、图片、效果和引用。
3. 将内容加入对应清单、敌群或奖励池，而不是误以为文件存在就一定会出现。
4. 运行内容校验和对应预览。
5. 调整后重新运行查看，并说明静态模板和现有存档实例之间的生效规则。

提供轻量快速预览：至少能直接体验样例人物战斗、获得并穿戴样例装备、触发样例事件。优先复用场景、调试入口与 Godot 检查器，不先造大型管理后台。

1. **装备闭环与资源基础**：以第三件全新装备验证 Resource → 内容注册 → 获得 → 背包 → 穿戴效果 → 保存续玩 → 图鉴。建立基础内容校验。

3. **事件、地点与奖励池闭环**：新增一个带条件和不同结果的事件，进入路线且奖励执行一次；保留确定性和待领取内容的续玩稳定性。
4. **录入体验与交付说明**：补齐中文说明、示例、校验反馈与快速预览；实际按说明手动创建内容验证一次，最终运行回归。
