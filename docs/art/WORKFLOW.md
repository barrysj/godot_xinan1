# Codex 美术生产与评审工作流

本文件是美术工作的主入口，统一说明生产、评审与备选流程。当前按单人开发组织：Codex 负责制作与技术管理，负责人通过看图和自然语言决定审美取舍。规范职责见[美术执行契约](ART_CONTRACT.md)，目录职责见[AGENTS.md](../../AGENTS.md#文档目录与归档规则)。

## 1. 职责与当前可用入口

- **Codex：**按现有方向设计概念、生成与处理资产、整理元数据、实现 Godot、技术检查、提出视觉问题并修复。
- **负责人：**分别批准概念、正式资产和游戏接入效果，决定审美取舍；不需要阅读 YAML、填写技术规格或维护登记表。自然语言反馈由 Codex 整理为可执行修改项及评审记录。
- **ChatGPT 网页版：**仅在负责人选择时作为生成或视觉复核备选，不是必经交接方，也不能代替负责人批准。

当前用 Codex 对话展示候选图和 Godot 实际截图，动作使用[现有预览入口](../battle-animation.md#独立动作预览)。每次展示包含资产名称、版本、评审阶段、图片或录像、本轮改动及当前待决事项；明确标出当前使用版与候选版。修改时并排展示两版，首次制作则展示候选本身；批量展示时提供编号与缩略图，点击可看原图。只提交当前阶段需要决定的事情，不要求负责人处理技术待办。

暂不开发历史图库、独立资产管理软件或 Serpent 二次开发，也不接入 Serpent、数据库或自动写回服务。只有找图、比较或确认当前版本持续阻碍实际制作时，再按具体问题评估工具。后续即便使用工具，也必须绑定具体版本并保存人工决定，不能把评分或标签直接等同批准。

## 2. 三阶段生产

每次围绕一个角色、一张场景或一个界面，先做成一个可用样本，再扩展同类资产。沿用当前美术方向，不借新任务重新设计全局风格。任务草案和技术参数由 Codex 整理。

```text
需求 → Codex 概念与任务草案 → 人工批准概念
     → Codex 正式资产与技术检查 → 人工批准资产
     → Codex 接入 Godot 与运行验证 → 人工批准接入效果
```

### 概念阶段

1. 明确用途、角色或场景身份、状态、资产数量与必要交付参数。已有规范明确的内容直接引用，不重复问。
2. 使用[模板](tasks/templates/VISUAL_TASK_SPEC_TEMPLATE.md)建立 `docs/art/tasks/<任务名>.md` 草案，删除不适用栏目。候选目录与保留规则见第 4 节，不为小任务建立多份阶段文档。
3. Codex 展示推荐概念及关键取舍，有明显分歧时最多补两个备选；负责人决定是否接受该方向。决定记录在任务内，通过后才制作正式候选。修改意见进入同一任务，不另建 handoff 文件。

### 资产阶段

1. 依据选定概念制作干净的正式候选；保留参考、生成提示词和实际输出，不覆盖待比较的旧版本。
2. Codex 执行第 3 节检查，再展示正式候选及必要的局部放大、透明底或动作预览，负责人决定是否接受该具体版本。技术通过只代表可交付，资产仍等待人工评审。
3. 负责人批准该版本后，将选定资产放入 `assets/art/`，登记 Manifest，资产状态为 `approved`，并关联任务评审记录。已存在的正式路径保持稳定，替换前记录版本；原文件通过 Git 或保留的候选版本追溯。

### 接入阶段

1. Codex 按已批准方案和资产接入，复用 Theme、组件和 Token；不得在此阶段顺手重设计其他区域。
2. 验证相关交互及 Godot 报错；视觉布局验证 1920×1080、2560×1440、1920×1200（16:10），在对话中输出实际运行截图。动画还须检查慢速、单步、暂停与出手时刻。
3. 技术验证通过后按项目规则提交本地 Git，任务仍可标记“接入待评审”；本地提交不代表视觉批准，不自动推送。
4. 负责人对截图或录像给出最终决定。若仅修接入布局，重评接入阶段；若改动已批准资产或概念，回到受影响阶段，其下游批准需重新取得。

新制作任务完成须具备三阶段的批准依据；已有批准方向和未修改资产直接引用原记录，无需重复审批。小修只重评受影响阶段，改布局无需重新批准未修改的角色原图。生成成功、技术检查和本地提交都不能替代人工批准。

## 3. 资产检查与登记

资产统一登记到 [assets/art/asset_manifest.yaml](../../assets/art/asset_manifest.yaml)，表内路径相对项目根目录。它由 Codex 维护资产索引、技术摘要、资源关联与状态，不是负责人的操作界面。Godot 当前不直接读取此表，但其中的信息仍有用途；保留 `portrait_region`、`anchor`、`normalized_canvas`、`animation_resource` 等有效字段。

### 参数依据与同步

| 信息 | 依据与维护方式 |
| --- | --- |
| 实际显示与播放参数 | 以 Godot 资源及实际执行的配置为准，例如头像裁切、显示锚点和动画引用；Manifest 保存查询摘要。 |
| 切帧与统一画布 | 以处理脚本及其配套元数据为准，核对生成的 Godot 动画资源；`normalized_canvas` 对应统一帧画布，不是原图分辨率。 |
| 实际文件属性 | 检查文件获得尺寸、透明度等信息，不以目标参数或旧登记代替。 |
| 资产批准与试接入授权 | 以人工决定记录为依据；Manifest 保存状态及引用，不从运行配置或目录位置推断批准。 |

每次修改或替换资产，由 Codex 同步核对受影响的资源、切帧数据和 Manifest 摘要；不要求负责人在多个文件中重复填写参数。发现不一致时查明实际使用值与批准要求，修正过期记录或任务范围内的实现，不直接用摘要覆盖运行资源。若修正会改变已批准视觉结果，按受影响阶段重新评审。当前不建设通用同步系统或新数据库，重复劳动明显后再补小工具。

### 交付检查

检查实际文件，不用生成工具的描述代替验证：

- 路径、文件名、格式、分辨率和用途一致；正式图不含概念标注框、说明文字或无关装饰。
- 需要透明时检查真实 Alpha、边缘及裁切，拒收烘焙棋盘格；角色比例、身份连续性仍需看图。
- 核对锚点、裁切、安全区域；NinePatch 记录边距。动作图集核对区域、统一画布、脚底与播放顺序，具体接入规则见[战斗动画](../battle-animation.md)。
- Manifest 只登记实际存在的资产，不用不存在的示例预占位置。必要字段：`file`、`type`、`resolution`、`transparent`、`usage`、`style_layer`、`status`；按用途补 `anchor`、`crop_mode`、`nine_patch`、`recolor_allowed`、图集及动画资源引用。
- 新批准记录用 `review_record` 引用任务文件；任务内记录相对路径、版本和 SHA-256。生成来源与提示词随资产保存在 `generation.md`，不复制通用规范。旧记录保留，不凭整理动作补造批准。

Manifest 状态仅描述资产：`concept` 是已有概念文件，`review` 是实际待评资产，`approved` 是负责人批准的资产版本，`deprecated` 是停用但保留追溯的资产。接入效果是否通过另见任务记录。

默认只有资产通过后才接入游戏。负责人明确要求提前试用时，可记录 `integration_authorization`（授权范围与来源）并保留 `review`；它只放行试接入，不跳过最终评审。历史上已授权接入的 6 项 `review` 资产保持原状态，不能自动批准或因本轮整理撤下。

## 4. 评审记录与版本

负责人可以回复“选第二版，颜色再淡一点”“人物可以，攻击动作太软”或“资产通过，游戏里显示得太小”，不要求专业术语或固定审批口令。Codex 根据当前展示对象记录阶段、文件版本及哈希、决定、意见、来源与日期；带修改意见的选择不等于批准修改后的新版本。只有意见而无明确批准时继续保留待评审，只澄清影响下一步的决定。

记录集中在对应任务的评审表，Manifest 只引用它。接入评审还记录被评审的代码提交、相关资产版本和截图/录像路径；未保存的临时截图不作为长期唯一证据。需留存的证据放 `design/concepts/<任务名>/review/`，可重建缓存留在 `.godot/`，不纳入正式资产表。

文件、批准稿或接入代码发生影响评审对象的变化后，不沿用旧版本批准。历史决定保留，新版本待评。没有历史概念证据的旧资产标记“未记录”，不补填“已通过”；重新开展该资产设计时再按流程评审。

### 有选择地保存版本

- 新任务中需要比较或继续修改的候选放在 `design/concepts/<任务名>/<资产名>/001/`、`002/` 等编号目录；最高编号仅表示最新候选，不代表已批准或正在使用。
- 保留选定稿、正在比较的候选及有明确复用价值的版本，不默认永久保存每次失败输出。已被评审记录引用的证据和用于验证的失败样本不作为普通废稿清理。
- 动画版本保存图片、切帧数据、必要的生成记录和对应的 Godot 动画资源；通过任务记录注明其资源对应关系，不只留下 PNG，不将新旧版本配套文件混用。
- 正式资产仍按角色、场景或效果组织，游戏引用路径保持稳定；替换前确保旧版及配套文件已在 Git 中可追溯，需要比较时再取出，不另建全量历史库。
- 已有资产不批量搬迁，不预建空版本目录；新任务使用上述方式。

## 5. ChatGPT 网页版备选

1. 负责人选择使用网页版，或 Codex 生图能力不可用时提出这个选项。不得默默切换到付费 API。
2. Codex 在对话中提供可复制任务提示词和明确附件清单：执行契约、对应领域 Spec、需要的视觉圣经章节、相关 Token、选定参考图片。附任务版本和目标阶段，避免上传全库。示例见[提示词](prompts/ART_PROMPTS.md)。
3. 负责人上传这些文件并发送提示词；网页版生成的是候选或 QA 建议，不是批准。
4. 负责人把原始输出附件上传到 Codex 对话，或保存到该任务的概念目录并告知路径。Codex 读取实际文件、记录来源、检查尺寸和透明度，纳入当前任务版本；不自动用网页输出覆盖整套规范。
5. 回到相同阶段由负责人评审。批准后继续本地资产登记、Godot 接入与效果评审，不再要求往返网页版。

## 6. 归档与维护

- `docs/art/tasks/` 只放具体美术任务及一个模板，按任务内状态区分进度；不预建空的 `active/`、`done/` 或每阶段一份文档。
- 长期规则回到相应主题规范；任务只保留选定参数、资产版本、批准和验证证据，不复制总方向。
- `design/references/` 存参考，`design/concepts/` 存候选及评审证据，`assets/art/` 存交付资产及其必要来源记录。已有失败样本与切帧工具保留，不为了目录整齐破坏验证入口。
- 只改规范、目录或配置且未改变运行画面时，检查链接、路径、格式、规则一致性与 Git 差异即可，无需启动游戏截图。

下一个实际美术任务用于验证这套流程：负责人能仅凭图片、预览和自然语言完成评审；Codex 能指出当前使用版、候选版及批准依据；替换后头像裁切、锚点、动画和配套元数据一致；接入效果有实际运行证据，涉及布局时完成第 2 节的三种分辨率检查。不为验证流程额外生成无需求的资产。
