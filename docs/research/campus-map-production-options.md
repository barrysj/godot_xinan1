# 校园大地图制作方案调研

日期：2026-09-17。代码读取基线：`8cc7208`。性质：研究建议，未批准的生产方案；研究子任务不生成美术、不安装软件、不接入游戏。DXF 内容统计来自同轮主代理实测，不能仅凭文件名断定其精度或完整性。

## 结论：运行时 2D，制作端 3D

建议制作一份可编辑、可重复渲染的简化 3D 校园母版，用锁定的正交相机输出日间、夜间、异常三套底图；游戏仍使用 **2D 大地图 + 独立路线与热点 UI**，支持平移、有限缩放、预览地点和确认前往。不是复制官网地图，也不是开放世界漫游。

这是针对当前玩法和成本的工程判断，不是 Godot 或 TopoExport 的强制要求。核心理由：玩家当前在选择下一站，不在操纵角色穿行建筑；几何、相机、锚点固定后，多态可以改变材质、灯光和装饰而不重新发明校园。实时 3D 不会自动变漂亮，仍需要建筑修形和美术设计。

| 方案 | 准确与重复性 | 多态表现 | 当前适配判断 |
| --- | --- | --- | --- |
| 官方 2D 图直接交互 | 原图不变时稳定 | 调色容易，但难形成独立美术和可信建筑光照 | 可作功能占位，不作为目标美术 |
| 分层 2D 矢量／插画母版 | 锁定路径后稳定 | 可做，立面与各态照明需更多人工 | 若最终接受纯平面风格，可选低成本路线 |
| **3D 母版离线渲染 → 2D 交互** | 几何、相机与导出参数受控 | 同模型批量出三态，局部修正可追踪 | **当前推荐** |
| 固定正交相机实时 3D + 2D UI | 同样能固定几何 | 连续灯光、动画、局部状态强 | 当连续动态变化是明确需求且设备验证通过时升级 |
| 可自由旋转／漫游的 3D 校园 | 需更多视角、遮挡和交互检验 | 自由度最高 | 当前无对应玩法收益，不推荐扩范围 |

正交投影不因距离改变物体大小，适合地图式表达；它不会自动修正错误模型。[Godot Camera3D](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)

## 项目证据与 UI 边界

- [CORE-02](../implementation/core-02.md) 已有三区域、七个共享逻辑地点、每路线四次访问，当前真实地图仍占位；[RUN-01](../implementation/run-01.md) 区分旧随机局与 M1 固定区域。
- [campus_region.gd](../../game/run/campus_region.gd) 保存逻辑地点 ID 与路线分支；`end_b/end_c` 仍是功能占位，不能据此虚构真实地标。
- [campaign_board.gd](../../scenes/expedition/campaign_board.gd) 是 `Control`，路线位置目前按步骤排列，不是真实地理坐标。背景替换不会自动完成地理地图接入。
- [M1 静态交付范围](../art/m1-static-assets.md) 要求区域图共享地点身份。推荐预渲染与此较一致；实时 3D 或新动态特效需单独确认范围，不能由本研究自动批准。

后续应把“路线状态”和“地图显示”分开：一个地点有稳定 `place_id`、世界坐标／底图归一化锚点；一条游戏路线有步骤和合法边。路径可以贴近真实道路，但可走与否由战役逻辑决定，不根据图片明暗推断。重复访问同地点时保留访问实例 ID，不能把地点 ID 当成一次访问 ID。

交互层采用容器／锚点布局，地图坐标经过统一变换映射到显示矩形，不硬写窗口像素。标签与点击区域不烘焙进底图；缩放时保持可读字号与可用点击尺寸。先选中预览，再用“前往”确认；触屏用点击代替悬停。键盘／手柄具备初始焦点、明确邻居与返回路径。锁定、可选、已访状态同时用形状／文字区分，不能只靠颜色。更新由路线／选择／显示状态事件驱动，非每帧重建全部 UI。

这些是 `game-ui-ux` 技能应用后的建议，尚未实现或验收。

## TopoExport 能提供什么，不能保证什么

官方应用的导出菜单包含 2D DXF、SVG，以及 3D DXF、OBJ、glTF 等；图层包括建筑、道路、水系、绿地与地形。菜单还把部分屋顶和植被标为 AI 功能。这说明它可以提供制作起点，**不证明用户这份导出包含所有图层，更不证明屋顶、楼高与校园真实一致**。[TopoExport 应用](https://app.topoexport.com/)

官网列有多种数据来源和区域覆盖，并对 LoD2 屋顶标注区域限制；本轮未找到清水河校区的测绘精度、楼高来源和完整屋顶保证。不要把外国区域的 LoD2 示例视作中国校园效果承诺。DTM 是地表，不包含建筑与植被；“有地形网格”也不等于“有真实建筑模型”。[TopoExport 官网](https://topoexport.com/)

具体导出需要检验：实体类型、图层、闭合轮廓、单位、坐标原点、Z 值、裁切范围、模型是否分栋，以及地标能否与用户照片／俯视图对应。一个非零 Z 值只能证明有高程，不能证明其为实测楼高。

发布前还需保存导出包的来源说明、账户导出条款和各底层数据许可。本轮公开页面未取得足以确认这两份文件商业再分发权限的完整条款，不能因可下载就宣称可自由商用。若数据来自 OSM，须处理署名及 ODbL 相关义务；对数据库与渲染成品应分别核对，不能简单推断整个游戏必须同许可。[OpenStreetMap 版权与许可](https://www.openstreetmap.org/copyright)

## 构建流程：一次定几何，多次定状态

1. **原始资料审计**：保存原始 DXF 与哈希、来源和导出区域；只读分析 2D／3D 文件。官方俯视图用于核对建筑与道路，不当成无条件精确测绘。
2. **坐标归一**：确认单位和坐标系，将校园移动到局部原点，保存逆变换；核对北向及轴转换。先以三个以上分散地标检验整体变换，再检查独立地标残差；如果有不同底图坐标系偏移，不可随手逐楼拖动来掩盖问题。
3. **建筑母版**：保留可用建筑几何，修正主楼订书针形轮廓、庭院孔洞、重要屋顶；楼高或细节无证据则标明估计，不称精确还原。道路、水面、建筑使用不同对象／集合。核心建筑精制，其余背景简化。
4. **锁定投影**：选择一个清晰可读的北向固定正交视角，保存相机变换、正交尺寸、输出尺寸、裁切和色彩设置。旧 007 是旧截图上的已批准关系，不能把其像素直接复制成新俯视图／3D 的米制坐标。
5. **三态设计**：日间调材质与植被，夜间调照明／自发光，异常态调受控装饰、色彩与覆盖物。地标坐标、主要轮廓和路线锚点不变。若异常需要真实移楼／断路，应另设显式几何与玩法变更清单，不能既变几何又宣称像素位置完全相同。
6. **输出资产与锚点**：同一相机导出三张图及遮罩、地标投影坐标；按审定缩放上限决定尺寸，必要时分块。界面名、路径、热点、锁定状态由 Godot 画，不由生图工具画。
7. **验收后接入**：逐版本进行概念、资产、接入审核；当前研究不升级任何旧候选的批准状态。

可重复意味着使用已冻结的输入和配置重新构建，而非反复在线重新导出或保持同一个生图 seed。应版本化：源文件哈希、修形对象、坐标转换、相机、材质预设、工具版本、随机植被 seed、锚点表。几何与锚点要求一致；跨显卡／渲染版本不承诺颜色逐像素相同。

## 现有 DXF 如何接上工具链

**优先利用现有文件，先检验再决定是否重导。** Blender 官方扩展站提供 DXF 导入扩展，但注明支持有限；不是默认保证各种 DXF 都完整导入。先导入小范围，比较对象数、边界、Z 范围和图层映射，检查重复面、法线、孔洞；不要把导入成功当作正确性证明。[Blender DXF 扩展](https://extensions.blender.org/add-ons/import-autocad-dxf-format-dxf/)

若 DXF 主要是建筑面网格，转成 Blender mesh 后整理；若仅是闭合 2D 轮廓，依据有来源的高度挤出；若只有等高线／无楼体，则不能声称它免去了建筑建模。若现有格式导入问题较多，可让用户在相同范围再导 glTF（优先）或 OBJ，并保存原始来源。无需在没有证据前要求购买订阅。

Godot 的推荐 3D 格式是 glTF 2.0，可接受 `.gltf/.glb`；DXF 不在其列出的原生 3D 场景格式内。直接导入 `.blend` 实际也会调用 Blender 转 glTF，因而建议保留 `.blend` 为制作源、显式导出 `.glb` 为运行时交换资产，以减少环境依赖。若采取推荐的离线渲染方案，Godot 运行时只需底图和锚点，不必加载 GLB。[Godot 支持的 3D 格式](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)

实时 3D 备选仍使用同一母版，不需要推倒重建；地点 UI 可通过 `Camera3D.unproject_position()` 从世界坐标投影到屏幕。[Godot Camera3D](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)

## 最小验证实验与决策闸门

这不是再画一张平面示意，而是验证导出几何是否能成为受控美术母版。先选导出范围中确实存在的一组核心地标；缺关键区域就停止对应生产、请求最少补充范围，不虚构填补。

1. 原样导入与俯视截图：核对主楼开口、湖岸、道路分离和建筑对应，列出缺失／估计项。若核心模型缺失严重，先补数据，不做三态美化。
2. 同模型同相机输出三态试片：至少一栋辨识度建筑、水面、一段道路；叠加统一 ID 遮罩，确认不因状态切换移位。建立人工认可的几何误差阈值，不能只验收“看起来差不多”。
3. 最小 2D 交互样本：相同三态底图切换、两个真实地点热点、一条合法路线、详情和前往。地理准确与美术认可分别审查。
4. 从干净输出目录重复构建，验证几何／相机／锚点哈希或数值一致；记录工具版本。检查 16:9、16:10、超宽和窄横屏，鼠标及键盘／手柄；真机没测则明确未验收。
5. 实测纹理显存、导出包体、加载和可读性。巨幅 2D 图不自动便宜：例如 8192² RGBA8 单层未压缩约 256 MiB，三态同时驻留约 768 MiB（不含 mipmap），应按缩放需要分块／懒加载，而非盲上大分辨率。

仅当用户明确需要自由视角、明显视差或持续几何动画，才将固定实时 3D／自由 3D 成本加入范围。Web 目标还需注意 Godot 当前 Web 导出仅使用 Compatibility／WebGL 2.0，不支持 Forward+／Mobile 渲染路径；因此桌面某些效果不能无条件照搬网页。[Godot Web 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
